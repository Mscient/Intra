# DR-10 — Clock, feed integrity and coverage methodology

Researcher: Codex, mechanics/model/feed assignment. Research/access date: **2026-11-05**, Asia/Kolkata. Scope: read-only methodology for saved NSE/SmartAPI observations and current Java diagnostic tools. **Pending independent review; no production thresholds or source values authorized.**

## Executive finding

Current tools can verify saved-byte integrity, compare wall/monotonic elapsed times, attribute sequence discontinuities, and reconcile decoded observations with caller-declared subscription windows. They cannot certify exchange-message completeness or UTC accuracy. A sequence number's presence is not evidence that it increments for every subscribed instrument update; a successful subscription is not proof of expected trading activity. No source-backed SmartAPI latency/clock SLA or global replay/sequence guarantee was established.

Two boundaries matter for G2: exchange clock obligations cannot be assigned to a retail client clock, and exchange/archive timestamps cannot be normalized without their exact epoch/zone meaning. The historical specification's jiffy conversion table contains an epoch-label/constant inconsistency identified below. No historical timestamp conversion is approved from that table alone.

**Completion review:** the v1.17 finding C3 is historical. DR-04's researcher opened the current linked **v1.19, dated 2026-08-03**, and confirmed the same epoch-label/constant conflict in §4 p58. Index records instead use native HH:MM:SS (§3.1.9 p56); do not apply order-jiffy conversion to index timestamps. Full/trim data and delivery delays also differ. See C8 and [DR-04](DR-04.md).

C3 arithmetic check: §6 calls its epoch “01-01-1980 12:00:00 AM GMT” but prints `315513000000000` microseconds. `1980-01-01T00:00:00Z` is `315532800000000` Unix microseconds, independently checked using .NET `DateTimeOffset.ToUnixTimeSeconds()`. The difference is **19,800 seconds (5h30m)**. This could reflect a local-epoch convention, but that explanation is an **inference**, not permission to relabel timestamps. ## Proposed metrics and event contract — question 2

All thresholds below are **unset owner-configured research parameters**, not exchange limits. Record threshold name/value/unit, owner, evidence/rationale, effective date and policy version. Precision, accuracy and latency are different fields. The C1 exchange requirement is not a permitted local-clock threshold.

| Metric | Definition / scope | Interpretation and necessary evidence |
|---|---|---|
| Local UTC offset | Estimated `local_wall − reference_UTC`, with sign, peer/ref source, sample time, dispersion/uncertainty, sync state and leap/smear policy | Requires authorized operator clock telemetry; no offset estimate from quote timestamps alone |
| Wall/monotonic divergence | For consecutive records in one process epoch: `Δwall − Δmonotonic`; also absolute magnitude | Detects steps/drift/measurement anomalies; cannot detect constant UTC offset |
| Observed source-to-receive age | Corrected receive UTC minus understood source event UTC | Report with combined source/local clock and timestamp-resolution uncertainty; not network latency or broker SLA |
| Inter-arrival silence | Elapsed monotonic time since last relevant observation, by source/connection/subscription/instrument/mode | Separate transport heartbeat, quote activity and expected activity; quiet instrument may be legitimate |
| Source sequence discontinuity | Compare raw values only within a source-documented domain and reset epoch | Without domain/completeness contract report numeric jump, not lost-message count |
| Future/stale timestamp | Compare source time interval with receive interval and configured freshness policy | If intervals overlap zero age, flag uncertainty; don't claim a negative transport duration |
| Reconnect duration | Defined milestones: disconnect observed, attempt, transport open, authentication, subscription acknowledgement, first eligible quote | Do not collapse transport-open into restored instrument coverage |
| Subscription coverage | Acknowledged interval intersected with intended instrument window | Control acknowledgement and actual observed quotes remain separate evidence |
| Journal lag | Receive-to-enqueue, enqueue-to-write, write-to-durable-commit monotonic intervals | Needs new stage timestamps; existing journal file integrity does not measure flush/durability latency |

Proposed records: `process_epoch_id`, `source_product_version`, `connection_id`, `subscription_id`, `instrument_id`, `mode`, `source_sequence_raw`, `source_sequence_domain_ref`, `reset_epoch`, `event_time_raw`, `event_time_unit_epoch_zone_ref`, `event_time_utc?`, `receive_wall_utc`, `receive_monotonic_ns`, `decode_start/end_ns?`, `write_completed_ns?`, `durable_commit_ns?`, `clock_sample_ref`, `clock_uncertainty?`, `expected_activity_ref`, `policy_ref`, `rights_ref`, `quality_flags`. Unknown optional values remain null, not zero. If monotonic timestamps cross process restart/boot, start a new epoch and leave cross-epoch elapsed time unknown unless a supported mapping exists.

## Current coverage command and expected activity — question 3

`instrument-feed-coverage-report` verifies raw/lifecycle inputs, joins caller plan windows by source/connection/subscription/resolved instrument, decodes raw quotes and counts observations inside/outside windows and acknowledgements. It reports acknowledged/unacknowledged duration, first/last receipt and timeline uncertainty. The implementation's windows are half-open `[start,end)` and quote assignment uses **receive UTC**. It unions overlapping acknowledged intervals rather than adding their durations. Its configured skew can affect quote-versus-ack matching; duration union is calculated from actual interval endpoints. A lifecycle anomaly can mark results uncertain globally. These are useful diagnostics, not independently expected activity.

The report does not prove that plan instruments should trade, all subscriptions were acknowledged by the real broker, every expected update arrived, raw capture started before the first provider message, or all decoded ticks were retained. It cannot infer intrawindow exchange completeness from a nonzero quote count. `expectedStartUtc`/`expectedEndUtc` names in output remain caller declarations.

| Independent evidence candidate | Proves / cannot prove | Required daily reconciliation fields |
|---|---|---|
| Dated exchange calendar, session/circuit/special-session circulars (DR-01) | Authorized trading windows/pauses; not at least one quote each minute | Document and amendment IDs, venue/segment/date/phase, event time, exceptions, reviewer |
| Dated instrument master and expiry/listing notices (DR-01) | Instrument identity and eligibility; not activity or delivery | Contract IDs, token validity, master timestamp, expiry and regime |
| Published provider feed specification and permitted operational notice (DR-02) | Contracted heartbeat/mode/conflation/sequence/reset semantics if explicit | Product/version, expected stream/mode, effective window, status/incident/correction refs |
| Authorized official historical records (DR-04), if subsequently provided | Independent event/volume comparison subject to matched definitions | Complete stream inventory, trade date, source counts, revisions, permitted hashes, matching coverage |
| Sanitized actual subscription/lifecycle receipts (owner) | Observed connection/auth/subscription events | Intended versus sent versus acknowledged versus decoded-instrument identity and times |

No independent expected-activity evidence was supplied for a concrete session. Therefore no observed session receives a completeness certificate in this report. Source catalogs refer to evidence to obtain through an authorized owner, not an instruction to scrape/acquire feeds.

## Exceptional conditions — question 4

Planned zero activity needs an independently sourced closure/ineligibility reason; otherwise label it `NO_OBSERVATION_EXPECTATION_UNKNOWN`. Holidays and special sessions select the correct date/version; do not infer closures from absent quotes. Auctions and pauses are separate states and can have different event types. Expired/delisted instruments exit the eligible universe at their sourced boundary. Provider outages and rejected subscriptions produce incomplete acquisition even when exchange trading continues.

Reconnect/reset opens a new sequence and lifecycle epoch. Without documented wrap width/behavior, a downward sequence change is not automatically a wrap, duplication, or broker fault. Equal timestamps can legitimately accompany different events; deduplicate by supported event identity/bytes, never timestamp alone. Wall-clock regression invalidates naive wall-time duration/ordering; preserve capture order and same-epoch monotonic evidence. When clock mapping is uncertain, retain raw event time and suppress precise cross-source age/synchronization claims. Reconnection does not imply gap replay or restoration of missed history.

## Completeness rubric — question 5

Proposed multidimensional rubric (`INFERENCE`); no single “green” score masks missing prerequisites:

| Dimension | PASS prerequisites | FAIL / UNKNOWN / NOT CERTIFIABLE |
|---|---|---|
| Saved-byte integrity | Framing/hash verification of exactly identified files | FAIL on malformed/hash mismatch; pass only means current bytes are self-consistent |
| Capture completeness | Independently reconciled receive/write counters, start/end lifecycle, durable boundaries and no unexplained drops | UNKNOWN without receive-path counters or with unverifiable pre-capture period |
| Instrument coverage | Dated independent universe/windows plus acknowledged subscriptions and observations compared to source-specific expectations | FAIL on evidenced missing required interval; UNKNOWN when activity contract absent |
| Exchange-message completeness | Documented all-event sequence/domain and initial state plus full-stream/gap/replay reconciliation | NOT CERTIFIABLE from broker snapshots without those guarantees, even with contiguous visible sequence |
| Clock comparability | Sourced field semantics plus contemporaneous local/source uncertainty evidence | UNKNOWN if constant offset, epoch conflict, missing mapping or unsupported clock guarantee |
| Data rights | Exact product/account permission, purpose, retention, backup, derived use and sharing reviewed | UNKNOWN without terms; other passes cannot override it |
| Research suitability | Study-specific fields, phases, synchronous coverage, costs and model scope independently reviewed | FAIL if study requires missing granularity; otherwise scoped conditional suitability, never “market complete” |

No freshness, drift, silence or reconnection numerical threshold is selected here. Owner/reviewer must distinguish normative source limits, provisional operational policies and empirically calibrated research criteria.

## Failure-mode tests and incident examples — question 6

All following cases are synthetic proposals unless later paired with an explicitly permitted real fixture. They test software handling, not broker behavior.

| Case | Expected outcome |
|---|---|
| Constant +30s wall offset, identical wall/monotonic intervals | Divergence test passes while UTC accuracy remains unknown; separate offset evidence catches it |
| Wall steps backward; monotonic advances | Regression flag, retain record order, no negative processing duration |
| JVM restart and reused connection ID | New process epoch required; no cross-process nanoTime subtraction |
| Sequence 10→13 with unspecified domain | Numeric discontinuity only; no assertion of two dropped instrument updates |
| Sequence down/up, repeated timestamp, max signed value boundary | Distinguish candidate reset/wrap/duplicate; unknown semantics and safe arithmetic, no guessed repair |
| Holiday/auction/pause/expiry window | Correct sourced phase/eligibility; never fabricate expected quote count |
| Subscription ACK absent, rejection present, or wrong token | Incomplete/uncertain instrument acquisition even if transport is healthy |
| Reconnect with ACK but no first quote | Control recovery observed; quote recovery unresolved |
| One quote in a full-day acknowledged window | Quote count one; no “complete session” conclusion |
| Event at end boundary | Outside the half-open window; exact boundary and skew behavior documented |
| Overlapping ACK intervals | Duration equals union, not sum; anomaly flags retained |
| Hash-consistent journal omits a pre-capture message | Byte integrity can pass while capture/exchange completeness remains unknown |
| Write stalls or storage full | If stage telemetry exists, lag/failure recorded; persisted prefix does not prove all receives were saved |
| Future event time within uncertainty interval | Uncertain age, not impossible negative latency; beyond uncertainty becomes an incident |
| C3 jiffy epoch alternatives | Reproduce 5h30 discrepancy; UTC conversion remains blocked pending source resolution |

Authorized-fixture follow-up requires owner-nominated existing captures plus rights, exact packet/document version, clock telemetry, actual lifecycle receipts, dates and independent comparison records. Compare raw/decoded counts, source identity, timestamp conversions and unaccounted records; investigate every discrepancy without synthesizing updates. Do not transmit orders to measure latency.

## Implementation consequences, owner inputs and handoff

Keep `RawCaptureClockAnalyzer` named as a divergence diagnostic. `InstrumentSequenceAnalyzer` currently scopes numeric comparisons to source/connection/subscription/instrument; this is a chosen diagnostic grouping, **not a verified SmartAPI increment contract**. `SmartApiV2NfoSnapQuoteDecoder` assumes epoch milliseconds and exposes packet sequence; its decoded L1 is insufficient for order-level completeness. `RawMarketMessage` records receipt wall/monotonic clocks but lacks explicit process epoch and durable-write milestones. Proposed additional fields require a versioned research contract and migration review; no code changed here.

Exact owner-input list:

1. **Project owner:** nominated already-authorized session/capture references, source/version, instrument/date scope, permission/retention/backup/derived-use terms. No identifiers, credentials, private addresses or raw data belong in the report.
2. **Project owner/operator:** sanitized clock evidence covering the session: OS/JVM version, clock source category, offset/error estimates and times, sync state, leap/smear policy, restart/boot boundaries and measurement locations. No assumed values.
3. **Project owner/operator:** sanitized actual intended/sent/acknowledged subscription mappings, reconnect/auth/first-quote milestones, drop/backpressure and durable-write counters; identify which are unavailable.
4. **Project owner:** choose provisional health thresholds and response authority with rationale and units; research provides the worksheet, not private tolerance values.
5. **Researcher:** finish current clock amendment review with DR-05, source timestamp/sequence semantics with DR-02, C3 epoch correction/known-time verification, and independent expected-activity sources with DR-01/04.
6. **Independent reviewer:** accept each dimension's prerequisites and any resulting session grading before G2 evidence promotion or future G4 health records.

No credentials, account/portal access, network feed, orders, broker contact or data acquisition occurred. No actual session completeness or live SLA is claimed. Hashes prove file identity, not authenticity, source completeness or legal sufficiency.
