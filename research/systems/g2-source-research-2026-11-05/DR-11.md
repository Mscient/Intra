# DR-11 — Recovery, reconciliation, and operational drills

Researcher: Codex `/root`. Date/access date: **2026-11-05** (Asia/Kolkata). Scope: offline Java research system, proposed future paper operations, and public systems guidance. Status: **research/design review candidate; G2/G4 remain open**. No operational drill was executed in this assignment.

## Executive finding

The repository has useful recovery primitives, but successful replay is not evidence that a broker account, feed, independent gateway, or operator has recovered. `oms-recover` reconstructs a completed single-contract run; deterministic checkpoints resume the single-contract simulator. Neither establishes external order truth. The local risk journal/facade now also has recovery support; its caller-maintained acknowledgement checkpoint must be distinguished from an independently protected trust anchor. The working tree changed concurrently during research, so implementation observations are bound to the file identities in [the local identity table](DR-11-13-local-source-identity.csv), not presented as release certification.

The following runbook makes every transition conditional on evidence. Public guidance supports testing recovery and verifying restored assets; the precise trading workflow, tolerances, deadlines, retention policy, and clearance authorities remain project design or owner decisions.

## Q1 — Recovery runbook and state transitions

The recovery controller is proposed. Its state is separate from trading-session date and cannot be cleared by renaming a session. Every transition records previous/new state, input evidence identities, operator/controller identity, wall UTC, monotonic timestamp plus process/boot epoch, and decision reason.

| State | Work and required evidence | Advance only if | Deterministic stop / next state |
|---|---|---|---|
| SAFE | Disable risk-increasing intents before loading strategy state; establish incident/recovery ID and exclusive writer lease | SAFE latch and ownership recorded | Lease conflict or inability to record latch: remain unavailable |
| VERIFY_RELEASE | Compare actual binary/config/reference/input bytes to separately retained accepted manifest; check schema and source review/permission validity | All required identities, versions and coverage match | Any mismatch/unknown rights: SAFE, preserve evidence, no silent substitution |
| VERIFY_HISTORY | Check raw/normalized/gateway chains; compare last acknowledged sequence/hash to independent receipt; locate eligible snapshot | Known start, complete acknowledged tail, correct lineage | Truncation/corruption/missing expected tail: SAFE; no automatic repair |
| RESTORE | Restore snapshot in a disposable offline instance; replay ordered tail once, rebuilding execution dedup, positions, reservations, strategy features and risk latches | Rebuilt state and intermediate/final hashes match frozen expected evidence | Unsupported schema/strategy or replay mismatch: SAFE |
| RECONCILE | Compare independent execution/position source, OMS, gateway and simulator at a common watermark; reconcile fees/settlement separately | Exact contract/quantity and terminal-order agreement; all missing events explained | Unknown order/position, differing watermarks, absent authoritative source: remain RECONCILE with new risk blocked |
| VERIFY_CONTROLS | Re-establish source/connection/subscription epochs; verify clock evidence, fresh marks, reviewed margins/rules, journal, watchdog/manual path | All readiness evidence current and required controls exercised | Any stale/missing fact: SAFE or RECONCILE; a connected socket is insufficient |
| AWAIT_RELEASE | Present incident disposition, residual risks, completed drills and readiness manifest | Authorized human release binds exact recovered state/config/incident and is still valid | Missing/stale/reused release: remain stopped |
| READY_PAPER | Permit only the reviewed paper session under the applicable gates | Ongoing liveness/freshness/reconciliation remain true | Any control loss immediately blocks new risk; K actions retain independent tracking |

For offline deterministic replay only, a missing checkpoint can cause replay from the verified beginning of the same immutable input set. This does not license discarding an acknowledged external-event tail. `oms-recover` is a completed-run audit, not step-by-step recovery of an interrupted portfolio or broker OMS. A future system may use these functions as evidence producers; it must not equate their success with the controller's final release.

## Q2 — Failure matrix and negative tests

| Injection | Required treatment | Evidence / negative assertion |
|---|---|---|
| Truncated/corrupt journal, changed hash or malformed event | Quarantine original; remain SAFE; restore only independently verified history | Fault offset, expected/observed identity; no repair, skipped record, or success status |
| Entire valid journal tail removed | Compare with protected acknowledgement watermark, not just internal chain validity | Truncated prefix must fail expected-tail check; absent external anchor is UNKNOWN completeness |
| Old but internally valid snapshot | Require lineage and complete replay to latest acknowledged boundary | Snapshot alone never establishes current position |
| Duplicate execution | Exact same scoped execution ID and payload is idempotent | Position, fees and reserved quantity change once |
| Reordered execution | Keep immutable receive order and source order; quarantine unresolved gaps or order causality | Never sort by wall-clock timestamp and assume completeness |
| Same ID, different quantity/side/price | Conflict incident; halt risk increase pending authoritative correction | Original bytes and both references retained; no overwrite |
| Unknown order / absent accepted order | Preserve independent execution truth and conservative unknown exposure | Do not drop a real execution because OMS lacks it; quarantine unsupported event path |
| Disconnect with cancel pending | Keep full still-possible fill reservation | No timeout-based release or fabricated cancellation completion |
| Unacknowledged/empty subscription | Affected instrument unavailable; record ack and message evidence separately | Connection success does not establish instrument coverage |
| Process/host restart | New monotonic epoch, SAFE start, ownership/fencing and complete reconciliation | No cross-boot duration subtraction; no automatic strategy release |
| Wall-clock step or missing clock evidence | Invalidate UTC age conclusions across discontinuity; retain monotonic local durations within epoch | Negative apparent age never becomes zero-latency evidence |
| Corrupted/new configuration | Fail identity/schema/effective-scope check | No default limit or replacement price/margin |
| Restore succeeded but notification/manual control failed | Hold release; record separate control failure | Recommended K action must not be labeled completed |

These are **specified tests, not executed tests**. Synthetic IDs and events are sufficient for implementation checks; external-behavior assertions require separately authorized paper evidence.

## Q3 — Independent reconciliation contract

Use an independently ingested execution ledger and independently obtained position/order snapshot, not a second serialization of OMS self-state. In offline fixtures, call it a **simulated independent oracle**, not broker truth.

Suggested normalized keys and fields:

```text
scope_key = (source_product, venue, segment, nonidentifying_account_scope,
             session_id, source_order_namespace)
contract_key = (venue, segment, underlying, kind, expiry_date,
                strike_decimal_or_null, call_put_or_null, contract_version)
execution_key = (scope_key, source_execution_id, source_trade_date)
event = {execution_key, correction_of, order_key, signed_units,
         price_inr_per_unit, trade_utc, receive_utc, source_sequence_or_null,
         knowledge_cutoff_utc, source_reference, input_sha256}
comparison = {recovery_id, common_watermark, contract_key,
              source_units, oms_units, gateway_units, simulator_units,
              working_residuals, unresolved_event_ids, status, reason}
```

Quantity, contract identity, execution IDs and lifecycle terminality use exact equality; no quantity tolerance. Money/valuation comparisons require a named unit, independently justified rounding policy and component scope; any permitted tolerance is owner/reviewer-supplied and never masks quantity disagreement. New acknowledgements/trades arriving after a snapshot require moving the common watermark and rerunning reconciliation. Terminal status alone cannot suppress already executed but late-reported fills, busts, or corrections. Unknown state blocks new risk. Settlement must reconcile position removal and cash/charges separately; a zero position does not prove cash reconciliation.

## Q4 — K0–K3 drill cards

Every drill has `kind = POLICY_MODEL | OFFLINE_ACTION_SIMULATION | AUTHORIZED_PAPER_OPERATION`. Report success only within that kind. Action tests below are future requirements; no network action is authorized here.

| Card | Trigger and setup | Required observation and pass condition | Reopen criterion |
|---|---|---|---|
| K0-01 | Feed stale/gap or clock uncertainty with open exposure | Record trigger, detection, recommendation; new-risk proposal denied; position monitoring continues; healthy dwell restarts after a missed observation | Reviewed healthy dwell with no gap; stronger latch absent |
| K1-01 | Independent position disagreement or gateway heartbeat loss with working orders | Record incident, human acknowledgement and each simulated cancel request/ack; reservations persist while pending; dropped ack remains unknown | Human clearance bound to reconciled order/execution/position evidence and healthy controls |
| K2-01 | Supplied hard-loss/margin/stress trigger; partially filled order plus route failure | Recommend cancel/protected reduce/halt; track cancel vs fill race and residual position; unavailable route yields unresolved exposure, never false flat | Reconciled residual risk, incident review, authorized clearance; policy alone cannot prove flat |
| K3-01 | Simulated compromised or hung strategy that ignores K1/K2 | Independent watchdog/manual-path tabletop; record isolation request separately from completion; preserve event evidence outside failed process | Verified restart, access review and all K1/K2 clearance evidence; human authority required |
| RESTORE-01 | Kill offline process between accepted event, durable write, acknowledgement and snapshot at each boundary | Restore only acknowledged identity or stop with explicit ambiguity; duplicate restart input cannot double position | Replay/reconciliation equality and release record |
| BACKUP-01 | Restore approved synthetic archive to isolated location with primary unavailable | Verify permissions/access, identities and complete chain; replay exact same result; time restoration | Reviewed RPO/RTO result and independent evidence acceptance |

Required timing fields are nullable facts, not filled from configured targets: `trigger_utc`, `detected_utc`, `recommended_utc`, `human_ack_utc`, `cancel_requested_utc`, `cancel_completed_utc`, `flat_verified_utc`, each with clock-quality and source. Local elapsed durations use same-epoch monotonic pairs. Detection/cancel/flat deadlines remain blank until selected and supported by route limits. A policy-model drill must leave cancel/flat completion `NOT_EXECUTED`.

## Q5 — G4 daily ritual and evidence schema

Pre-open: authorized operator identifies session, reviews rule/master diffs, validates release/input identities, source rights, calendar, risk limits, marks/margins, clock, journal, watchdog/standby, operator/manual path and unresolved incidents. During session: monitor source-specific freshness/coverage, latches, reconciliation, cancellations and residual risk; preserve configuration lineage. At close: reconcile orders, unique executions, signed positions, settlement/costs and simulator; review completeness/fill limitations; archive evidence and operator disposition.

```text
daily_record = {schema, campaign_id, session_id, calendar_version,
  session_class, build_identity, config_hash, rule_review_ids, rights_review_id,
  input_manifest, start_watermarks, end_watermarks,
  preopen_checks[{id, observed_at, status, evidence_ref}],
  actual_coverage, completeness_status, reconciliation_status,
  cost_and_fill_review_ref, drills[], incidents[], archive_receipt,
  operator_signoff_ref, complete_session, preopen_pass, exclusion_reason}
```

`complete_session` requires the entire required session coverage and all mandatory evidence. Partial-session pipeline tests, disconnected periods with no reviewed expectation, synthetic replay, or missing post-close signoff cannot count toward observed paper sessions. Maintain an append-only campaign ledger with scheduled sessions and explicit exclusions. A failed/missed required pre-open check breaks the consecutive passing streak; do not omit the day to preserve it. **20 consecutive passes and 60 complete sessions are plan acceptance criteria, not NSE/SEBI rules.** Severe unresolved incidents block promotion even if counts are met. Campaign eligibility/reset details require an owner-reviewed protocol before collection.

## Q6 — Backups, retention, and reset

Maintain a manifest linking original bytes, parser version, corrections, acknowledgements, source/permission references, storage location class, access roles, backup receipts, restore tests, retention basis, expiry and legal hold. Hashes demonstrate byte identity only. A separate controlled checkpoint/receipt is needed to detect replacement of an entire locally consistent chain. Test restore without using the primary files and without creating a second active writer.

No retention duration or region is selected. The plan's eight-year phrase does not establish applicability to this own-account research corpus. DR-04/05 and account contracts must resolve allowed local storage, backups, derived results, deletion and legal holds. Deletion requires a reviewed inventory across replicas and a non-sensitive deletion record; this research performs no deletion. Reset synthetic paper fixtures under a new run ID while retaining prior lineage and incident state. Session rollover alone cannot erase an unresolved incident or permit clearing external positions.
