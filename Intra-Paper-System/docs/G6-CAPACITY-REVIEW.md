# G6 tier and capacity review v1

This is a standalone, offline Java 21 evidence reviewer. The software deliverable does **not** close G6. G6 remains **INCOMPLETE** until verified evidence from at least six calendar months of an authorized optional G5 pilot and qualified independent review exist. **No scale-up is authorized.** Neither a report nor an owner/reviewer record enables orders, changes a tier, changes risk limits or closes a gate.

Baseline inspected: `origin/main` at `7d6f6c56424b4e50903121eaf8ee491a9ce15607`. Its trackers record G0 open, G1/G2 incomplete, G3 blocked/incomplete, G4 not started, G5 not authorized, and G6 not started. “G5 closed” in the G3 packet means the live route is closed. It is not six-month operating evidence. There is no G5 authorization verifier or external broker-ledger reconciliation subsystem in this baseline. Unrelated implementations in other worktrees were not imported.

## Status and authentication boundary

| Result | Meaning | CLI exit |
| --- | --- | --- |
| `FAIL` | Contradictions, changed bytes, invalid signature, protocol violation, identity mismatch, reconciliation failure or revocation | 1 |
| `INCOMPLETE` | Missing, excluded, unauthenticated, unsupported or synthetic evidence | 2 |
| `ELIGIBLE_FOR_HUMAN_DECISION` | Maximum permitted future result; never authority to trade or scale | 0, reserved |

The current revision deliberately cannot produce eligibility: it has no independently provisioned identity trust store, authenticated G5 authorization adapter, authenticated broker provenance or qualified independent-review attestation. These are explicit findings, not caller-controlled booleans. Supplying an `APPROVE` or valid signature does not remove them. All reports include `diagnostic_only=true`, `performance_claim_eligible=false`, `g6_closed=false` and `scale_authorized=false`. A mathematically valid Ed25519 signature is labeled separately from independent authentication. No reviewer or owner decision is reported as verified.

Missing data stays null/unknown. `FAIL` takes priority over recorded incomplete findings. Invalid structural input is a protocol failure; absent files are incomplete. An invalid history that cannot support an analysis event is rejected before report publication. The explain command still returns a deterministic failure diagnostic.

## Input contracts

Versioned JSON Schemas live in [schemas/g6-capacity-review](../schemas/g6-capacity-review). Java enforces the semantic contract without downloading a schema or loading external code. JSON duplicate keys, unknown contract fields, malformed UTF-8, invalid dates/enums/digests, duplicate records and noncanonical order are rejected. Required-but-unknown references/parameters use explicit null; do not omit fields or invent zero/default values. Lists of instruments are sorted, unique and nonempty. Files are limited to 16 MiB, the dossier to 256 MiB, arrays to 100,000 entries; these are resource bounds, never evidence/sample-size thresholds.

The dossier root contains `manifest.json` and portable relative paths to immutable inputs. Every reference has exactly `path` and lowercase `sha256`. Original bytes, including whitespace, are hashed. There is no network access, credential input, broker adapter or executable command in any contract.

The manifest also requires `account_currency` and nullable `identity_evidence`. The latter binds original snapshots for every identity, including the tested JAR whose `Build-Commit` must match. Missing snapshots remain incomplete. Daily risk configuration hashes must match the registered configuration. Calendar sessions bind exact `start_utc` and `end_utc` windows; the daily evidence must cover those exact windows. Closed dates have null windows. Source and expected-hash inventories distinguish missing bytes from verified byte identity.

1. **Manifest:** review ID, exact pilot ID, sorted instrument scope, exact `[evidence_start,evidence_end_exclusive)` dates, owner and separate reviewer roles, deployment/execution description, protocol/calendar/scenario references and optional G5 authorization reference. Identity fields bind strategy, tested Git build commit, configuration, instruments, rules, calendar, costs, risk, account route, deployment, data sources and execution. Every session must match all identities. A changed identity requires a new review; it cannot inherit a smaller tier’s evidence.
2. **Protocol:** registered time, explicit descriptive method, thresholds, units, per-session aggregation, rationale and separate owner/reviewer approval documents. A protocol core digest omits only the two approval references to avoid a circular digest. An approval binds that core. The manifest registration binds the complete protocol and approvals before analysis. Event/registration timestamps are caller declarations, not trusted proof of preregistration. No universal profitability, Sharpe, drawdown, sample-size or capacity threshold is supplied. Empty thresholds are incomplete. Supported comparisons are `LE`, `GE`, `EQ`; the only current aggregation is `EACH_SESSION`. Unsupported statistical methods fail rather than silently substituting a method.
3. **Calendar:** timezone and one row for **every calendar date** in the interval. A scheduled date has one session ID. `CLOSED` needs a reason and null session; `EXCLUDED` needs a reason, is retained, and leaves coverage incomplete. Missing calendar days and sessions are explicit findings. Exactly six calendar months means `end_exclusive >= start.plusMonths(6)`, including the usual end-of-month calendar adjustment. Calendar span is reported separately from eligible live evidence. Six synthetic sessions or six synthetic months never qualify. V1 supports one operating session per calendar day; multi-session calendars need a separately versioned contract.
4. **Operating session:** identity/date/scope, original source classification, observation status, daily-operations bundle, normalized broker records plus exact original export references/provenance, optional applicable portfolio artifacts, declared joint conditions, additional source-bound observations, and exception records. `SYNTHETIC`, `REPLAY_ONLY`, `SIMULATED`, `ESTIMATED`, `CALLER_SUPPLIED` and `CLAIMED_LIVE_G5` remain distinct. The last value is a claim, never authentication. Synthetic underlying daily/broker evidence presented as live fails. All unresolved exceptions fail; a risk halt is retained and requires applicable preregistered disposition. Resolved incidents do not establish operational readiness.
5. **Scenarios:** owner’s tier ladder, strategy/route identities, instruments, maximum order size, participation, exposure, order rate, risk budget and broker/exchange limits. Unknown values are null. These declarations are not changes to configuration. They are compared against each **jointly recorded session vector**, not a combination of maxima from different sessions. Exact matches remain unauthenticated; lower proposals are `WITHIN_RECORDED_BOUNDS_UNTESTED`; larger, changed-identity or unsupported proposals are `UNTESTED`. This is not an inferred capacity frontier or a statement of permissible risk.
6. **Decisions:** reviewer/owner role and identity, qualification and independence evidence references, exact source inventory, exact report SHA-256, reviewer software Build-Commit and code hash, decision, limitations/reservations, and optional signature. Reviewer decisions precede owner acceptance/rejection of the recommendation. A decision cannot grant scale authority, erase limitations or turn a report into a gate closure.

## Reconciliation and observations

`DailyOpsEvidenceChecker` is rerun for each daily bundle. It checks input/replay byte identity, feed windows/staleness, risk reservations/events, order/fill linkage, fees, settlement, flat closing positions/cash and operator/incident records. Its original contract remains caller-supplied and supports flat sessions; unsupported overnight/other event semantics are not silently added. Source bytes are snapshotted for hash/parse consistency and rehashed after analysis. Existing portfolio replay/accounting, risk-artifact and settlement-artifact verifiers run when their artifacts are supplied. Artifact-only risk/settlement verification is labeled as such, not re-performance of an external live audit.

Broker reconciliation in v1 compares supplied normalized risk/order/fill events, executions, positions, initial/ending cash, fees, settlement events and charge lines exactly against the existing daily ledger. It preserves original broker export bytes and a normalization-protocol reference. Strict `g6-stream/v1` documents add acknowledgements, rejects, cancellations, corrections, external cash flows and margin samples. Each stream has an explicit expected count, completeness declaration, source classification and a reason when empty. Acknowledgements must follow submission and precede fills; rejected orders cannot have fills; cancellations must match risk reservation releases. Corrections retain original and corrected records, chain successive changes, and end at the reconciled ledger record. Opening cash flows must explain cross-session cash changes in the declared account currency; intraday external cash flows remain unsupported by the existing flat-session accounting contract. Missing sessions reset continuity and remain incomplete.

There is **no independently authenticated broker-format decoder**. These joins check supplied normalized bytes and never authenticate export provenance, normalization or completeness. Missing streams remain incomplete. Margin diagnostics report the maximum sum of simultaneous, scope-complete supplied samples, with a proxy/source label; they do not calculate exchange margin or a permissible capacity. Path-based daily and portfolio verifiers receive private immutable copies of the exact hashed bytes. No trading/accounting calculations were changed.

Descriptive normalized observations include maximum order/fill units by instrument, submitted/filled quantities, count of orders/fills, partial/missed orders, turnover, fees, flat-session realized/unrealized P&L, peak orders per UTC second, quantity fill ratio, halts, incidents and broker-stream diagnostics. Fill ratio uses 12 decimal places and HALF_EVEN solely for descriptive display. Financial values reuse reconciled daily amounts. Unknown exposure, participation, slippage and drawdown remain null unless separately supplied, in which case they appear only under `supplemental_unverified_observations`, preserving their basis and source. No aggregate Sharpe, capacity extrapolation or live performance claim is generated. Supplemental estimates cannot satisfy thresholds or establish verified bounds. Threshold comparisons run only after both exact-protocol signed approval declarations are supplied; their identities still remain unauthenticated. Read observations together with source classification, reconciliation status, units and authentication fields. Missing/excluded/unreconciled sessions cannot contribute vectors to the scenario comparison.

Existing DSR/PBO/HAC protocols and calculations are unchanged. An external statistical-protocol file can be bound and retained, but G6 v1 does not invent or execute a statistical protocol. Top-of-book snapshots and simulated fills never establish tested capacity.

## Append-only history and signatures

History is an immutable snapshot of ordered events. Registration is first and unique. Each event has a zero-based sequence and the SHA-256 of the preceding canonical event (all-zero initial link). Types are `REGISTRATION`, `EVIDENCE`, `CORRECTION`, `ANALYSIS`, `REVIEWER_DECISION`, `OWNER_DECISION`, `REVOCATION`. Corrections point to an active prior evidence event and retain its originals. They replace its logical position, not its bytes. Revocation points to a prior event; a revoked review requires a new review identity.

Canonical JSON sorts object keys, preserves array order, uses exact decimal plain notation, UTF-8, and one final LF. An event digest includes its signature. Ed25519 signs canonical object bytes with the `signature` member **removed**. Keys are base64 X.509 SubjectPublicKeyInfo; signatures are base64 raw Ed25519. Invalid signatures fail. Self-supplied valid keys prove only possession of that key, not identity, role, qualification, independence or historical signing time.

`review` atomically publishes `report.json`, `artifact.json`, the exact `input-history.json`, and `history.json` extended by one analysis event bound to the report digest. The analysis timestamp copies the last caller event time; it is deterministic and explicitly not an observed trusted clock. The report binds its pre-analysis history head and exact input-history bytes, avoiding a circular hash. Later decisions extend the published history and bind the report/build. `verify` recomputes every referenced source hash, history link, report bytes, reviewer code/build identity, and supplied signatures. It rejects changed/reordered histories, stale decisions and an extension containing newer evidence/analysis. Verify older generations against their archived input history; provide the latest extension to detect later decisions or revocation.

An analysis event embeds its canonical report in `report`; every other event has `report=null`. Historical analyses reproduce against their exact preceding history prefixes, including all retained original dependencies. Owner decisions bind `reviewer_decision_sha256` as well as the report and build; reviewer decisions have a null recommendation reference. Revocation is terminal. History snapshots must be canonical byte-for-byte. Verification of a reproducible incomplete report with missing source files reports `integrity_verified=false`; reproducibility alone does not prove those missing source hashes.

The append helper publishes a **new directory containing history.json** and never updates its input. Registration/event creation and signing are explicit offline custody operations. The subsystem has no private-key provisioning or trusted timestamp service. Retain all prior generations in independently controlled archival storage. A local hash chain cannot prove that no entire alternate history was fabricated, no unprovided tail exists, or all activity was logged. Independent anchoring/custody remains necessary.

Publication uses forced files, a local writer lock and an atomic directory move with no replacement or fallback. Paths reject traversal, absolute/UNC paths, case aliases, hard-link aliases and symlink/reparse ancestors. Outputs must be outside inputs and must not already exist. The input/output parent directories must be controlled by the operator; this is not a sandbox against a privileged adversary racing filesystem mutations or deleting entire generations. Atomic visibility is not a claim of independently verified power-loss durability.

## Commands

Build with the existing Java 21 `build.ps1` from a clean commit; the separate CLI is packaged automatically. Trading/shared CLI entrypoints remain unchanged.

```powershell
$env:JAVA_HOME = 'C:\Program Files\Microsoft\jdk-21.0.13.21-hotspot'
$env:INTRA_PAPER_BUILD_DIR = 'C:\review-build'
./build.ps1
$jar = 'C:\review-build\intra-paper-system.jar'
./g6-capacity-review.ps1 -Command explain -JarPath $jar
./g6-capacity-review.ps1 -Command review -Dossier C:\dossier -History C:\dossier\history.json -Output C:\reviews\generation-1 -JarPath $jar
./g6-capacity-review.ps1 -Command verify -Dossier C:\dossier -Output C:\reviews\generation-1 -JarPath $jar
./g6-capacity-review.ps1 -Command append -History C:\reviews\generation-1\history.json -Event C:\custody\reviewer-event.json -Output C:\reviews\generation-2 -JarPath $jar
./g6-capacity-review.ps1 -Command verify -Dossier C:\dossier -Output C:\reviews\generation-1 -History C:\reviews\generation-2\history.json -JarPath $jar
./test-g6-capacity-review.ps1 -JarPath $jar -OutputRoot C:\g6-tests
```

Direct entrypoint: `java -cp intra-paper-system.jar com.mscient.intrapaper.review.g6.G6Cli`. `explain` without inputs and successful append return 0 for command completion, not eligibility. A successful integrity verification of an incomplete report still exits 2. Source-class testing uses `UNPACKAGED`; production verification binds the JAR’s `Build-Commit` and a digest of all Intra class bytes. A report cannot be verified with a different build and silently relabeled.

The test runner generates complete and negative **synthetic** dossiers. The sparse synthetic calendar is a parser/coverage fixture, not an exchange schedule, live history or sample-size qualification. The checked-in example is also synthetic. No profitability, legal-compliance or trading-readiness conclusion follows from software/synthetic checks.

`test-g6-schemas.ps1` validates generated dossiers and reports with all schema references resolved from preloaded local files. It never enables external fetching. JSON Schema covers structure; Java additionally checks identities, chronology, reconciliation, hashes, signatures and path safety. To review the checked-in example, use `examples/g6-capacity-review/dossier` as the dossier and its `history.json` as history, with a new output directory outside that dossier. Expected review and verify exits are 2 (`INCOMPLETE`).

## Outstanding owner/reviewer evidence

G0–G5 prerequisites and an actual optional pilot authorization; exact deployment/route/rule/cost/risk identities; original authenticated broker and operating exports; a reviewed complete session calendar and at least six calendar months of qualified evidence; complete external-ledger/fee/settlement/margin/feed/restart/stop/incident reconciliation; source and normalization authentication; an explicit preregistered and separately approved threshold/decision protocol; an owner-declared scenario ladder with unknowns preserved; qualified independent review with authenticated independence/custody; separate owner acceptance or rejection of the exact report. Additional supported source adapters and independently provisioned authentication are required before this v1 engine could ever report eligibility. Software checks cannot provide those decisions.

Any eventual recommendation applies only to the exact tested strategy, instruments, build, configuration, data sources, costs, risk limits, execution/deployment conditions and jointly tested size envelope. A proposed next tier always needs separate owner and independent-review decisions.
