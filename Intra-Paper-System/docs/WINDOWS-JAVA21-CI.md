# Windows Java 21 offline CI

The workflow is [`.github/workflows/java21-build.yml`](../../.github/workflows/java21-build.yml),
named **Windows Java 21 offline validation**. It runs on `windows-2025` for pushes
to `main`, pull requests targeting `main`, and manual `workflow_dispatch` runs.
There are no path filters. A run has a 20-minute timeout; a newer run for the same
ref cancels the previous one. The job needs only `contents: read`, and checkout
does not persist credentials.

## JDK and inputs

[The installer](../../.github/scripts/install-microsoft-jdk21.ps1) downloads the
versioned Microsoft Build of OpenJDK **21.0.13.0.2 LTS**, Windows x64 ZIP, verifies
its pinned SHA-256, and sets `JAVA_HOME` and `PATH`. The version and checksum come
from [Microsoft's download page](https://learn.microsoft.com/en-us/java/openjdk/download)
and its linked `microsoft-jdk-21.0.13.0.2-windows-x64.zip.sha256sum.txt`.
Update both pins together when changing the supported version, and update the
version check in the CI runner. The explicit archive avoids relying on
`setup-java` matching Microsoft's five-part release identifier.

Tests use committed synthetic examples and fixtures generated by the committed
Java tests. No market data is downloaded, no broker service is contacted, and no
secrets or account credentials are configured. GitHub Actions and the JDK are the
only downloaded tooling; the production build has no dependency download step.

## Suites actually executed

[The CI runner](../../.github/scripts/test-offline-ci.ps1) invokes
`Intra-Paper-System/test-offline.ps1`, which runs the dependency-free Node
`test-offline.mjs` runner. It compiles all Java sources and explicitly executes
26 test, fixture, and pricing-validation entry points. Unlisted executable mains
cause a failure. See [offline verification](OFFLINE-VERIFICATION.md) for commands
and current local evidence.

| Area | Entry points covered |
| --- | --- |
| Single contract | Admission/identity regressions and core execution/journal/checkpoint/OMS plumbing |
| Data/reference/market data | Synchronized frames, dated mapping, sequence and feed-coverage tests |
| Risk and local stop policy | Gateway durability, 308-child-JVM process recovery, operational kill controller |
| Portfolio | Accounting, replay, dated costs, artifacts, settlement, settlement fixture generation, risk replay |
| Audit/evaluation | Risk and settlement audits/fixtures, external-ledger reconciliation, trial evaluation, holdout controller |
| Offline operations/permissions | Incident drills, daily evidence, intended-use preflight |
| Mathematical pricing | Java R11, boundary and no-arbitrage harness outside the runtime JAR |

The separate pinned QuantLib-Python comparison is not included and requires its
own preinstalled environment. All Java entry points are executed, but synthetic
coverage does not establish source authenticity, data rights, calibrated fills,
power-loss safety, statistical validity, or trading performance. Hosted CI for
this uncommitted increment has not been executed or externally inspected.

Every Java process exit code is checked. All suites are attempted after successful
compilation even if one fails; any failure makes the CI step fail and skips the production
build. After all suites pass, `Intra-Paper-System/build.ps1` creates
`intra-paper-system.jar`. CI reads `META-INF/MANIFEST.MF` from that actual JAR,
unfolds continuation lines, and requires exactly one `Build-Commit` equal to both
`git rev-parse HEAD` and `GITHUB_SHA`. For pull requests this is the checked-out
GitHub merge revision, not necessarily the contributor's branch tip. Dirty or
unknown build identities fail this check.

## Logs and artifact retention

| Path on runner | Contents / artifact |
| --- | --- |
| `${RUNNER_TEMP}/intra-paper-jdk/install.log` | Pinned JDK version, archive URL, expected/actual SHA-256, installation status |
| `${RUNNER_TEMP}/intra-paper-ci/logs/environment.log` | JDK vendor, Java/runtime/compiler versions, PowerShell version, source and expected commit, planned suites |
| `${RUNNER_TEMP}/intra-paper-ci/logs/<suite>.log` | Runner name, source commit, stdout/stderr, result and exit code |
| `${RUNNER_TEMP}/intra-paper-ci/logs/production-build.log` | Production build output and exit code |
| `${RUNNER_TEMP}/intra-paper-ci/logs/manifest-check.log` | Expected and embedded commit, verified JAR SHA-256 |
| `${RUNNER_TEMP}/intra-paper-ci/logs/summary.log` | Overall status and actual `PASS`, `FAIL`, or `NOT_RUN` result for every suite/check |
| `${RUNNER_TEMP}/intra-paper-ci/logs/failure.log` | CI exception, when a failure occurs |
| `${RUNNER_TEMP}/intra-paper-ci/package/intra-paper-system.jar` | Production JAR, uploaded only after successful validation |

The workflow uploads logs with `always()` as
`offline-validation-logs-<github.sha>-<github.run_attempt>`, including on test or
manifest failure. It uploads the verified JAR separately as
`intra-paper-system-<github.sha>-<github.run_attempt>`. Both artifacts have
**14-day retention**. Missing artifact files are errors. The Actions step summary
also lists the source commit, JDK version and actual suite/check results.
Generated fixture directories, compiled test classes and intermediate JARs are
not uploaded; the retained text contains the focused runners' concise output.

## Reproduce and verify failure propagation

Use a clean checkout containing the workflow changes and the supported Microsoft
JDK. From the repository root:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-21.0.13.0.2+1'
.\.github\scripts\test-offline-ci.ps1 `
    -OutputRoot (Join-Path $env:TEMP 'intra-paper-ci-local') `
    -ExpectedCommit (git rev-parse HEAD)
```

To test the installer locally, pass `-InstallRoot` explicitly. Logs/builds must
be outside tracked source paths so the build's clean-checkout identity remains
valid. The existing replay/evaluation runners also use ignored
`Intra-Paper-System/build/` output paths.

Use short checkout/output paths on Windows: the existing runners pass source
paths directly to `javac`, so deeply nested copies can exceed Windows command
line or file path limits. GitHub's normal checkout and `RUNNER_TEMP` paths are
short. Local acceptance evidence is recorded in
[the validation report](../../research/systems/2026-11-06-windows-java21-ci-validation.md).

For hosted acceptance, after authorization to push a test branch, open a pull
request targeting `main` and retain the successful run URL and artifact names.
On a separate disposable commit, insert
`if (args.length == 0) throw new AssertionError("intentional CI failure");`
at the start of `PortfolioAccountingLedgerTest.main`. Its runner passes no
arguments, so the Java test fails. The workflow must finish nonzero, retain a
`portfolio-accounting.log` with the assertion and nonzero exit, report that
suite as `FAIL`, and report production build/manifest as `NOT_RUN`; no production
JAR artifact should be uploaded. Restore the test in the disposable branch.
Never include the deliberate failure in the proposed production change.

Local execution verifies runner/build/failure behavior but is not evidence of a
hosted Actions run. A hosted test-branch run requires separate push authorization;
neither this workflow nor its scripts push or merge code.
