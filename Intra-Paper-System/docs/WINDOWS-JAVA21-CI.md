# Windows Java 21 offline CI

The workflow is [`.github/workflows/java21-build.yml`](../../.github/workflows/java21-build.yml),
named **Windows Java 21 offline validation**. It runs on `windows-2025` for pushes
to `main`, pull requests targeting `main`, and manual `workflow_dispatch` runs.
There are no path filters. A run has a 20-minute timeout; a newer run for the same
ref cancels the previous one. The job needs only `contents: read`, and checkout
does not persist credentials.

## JDK and inputs

[The installer](../../.github/scripts/install-microsoft-jdk21.ps1) downloads the
versioned Microsoft Build of OpenJDK **21.0.13.0.2 LTS**, Windows x64 ZIP, verifies
its pinned SHA-256, and sets `JAVA_HOME` and `PATH`. The version and checksum come
from [Microsoft's download page](https://learn.microsoft.com/en-us/java/openjdk/download)
and its linked `microsoft-jdk-21.0.13.0.2-windows-x64.zip.sha256sum.txt`.
Update both pins together when changing the supported version, and update the
version check in the CI runner. The explicit archive avoids relying on
`setup-java` matching Microsoft's five-part release identifier.

Installation requires an absent or empty ordinary directory below `RUNNER_TEMP`
(or the system temporary directory for local use). The installer rejects the
temporary root itself, paths outside it, files, and reparse points in existing
ancestors before writing or downloading. It never overwrites an existing
installation. CI checks the release metadata and the executable Java/vendor and
compiler versions against the exact pin.

Tests use committed synthetic examples and fixtures generated by the committed
Java tests. No market data is downloaded, no broker service is contacted, and no
secrets or account credentials are configured. GitHub Actions and the JDK are the
only downloaded tooling; the production build has no dependency download step.

## Suites actually executed

The G1 increment adds `test-hypothesis-card.ps1` as the fourteenth selected source
suite, plus a production-JAR repeat. It checks strict complete cards, exact hashes,
version preservation, false approval/permission/gate claims and synthetic/proposed
trial separation. See [the registry contract](HYPOTHESIS-CARD-REGISTRY.md).
These are software checks; G0/G1 remain incomplete.

[The CI runner](../../.github/scripts/test-offline-ci.ps1) invokes these existing
PowerShell runners sequentially, each in a separate `pwsh -NoProfile
-NonInteractive -File` process:

| Runner under `Intra-Paper-System/` | Java entrypoints executed |
| --- | --- |
| `test-risk-gateway.ps1` | `RiskGatewayDurabilityTest` |
| `test-risk-gateway-process.ps1` | `RiskGatewayProcessTest` |
| `test-portfolio-replay-engine.ps1` | `PortfolioReplayEngineTest`, `PortfolioExecutionCostScheduleTest`, `PortfolioReplayArtifactVerifierTest`, `PortfolioSettlementTest` |
| `test-portfolio-risk-replay.ps1` | `PortfolioRiskReplayTest`, plus the four replay/cost/artifact/settlement entrypoints above |
| `test-portfolio-accounting.ps1` | `PortfolioAccountingLedgerTest` |
| `test-portfolio-risk-audit.ps1` | `PortfolioRiskAuditTest`, `PortfolioRiskSettlementFixtures` |
| `test-portfolio-settlement-audit.ps1` | `PortfolioSettlementAuditTest` |
| `test-portfolio-trial-evaluation.ps1` | `PortfolioTrialEvaluationTest`, `PortfolioReplayEngineTest`, `PortfolioExecutionCostScheduleTest`, `PortfolioReplayArtifactVerifierTest` |
| `test-daily-ops-evidence.ps1` | `DailyOpsEvidenceCheckerTest` over committed synthetic evidence bundles |
| `test-dataset-intended-use-preflight.ps1` | `PermissionPreflightTest` over synthetic permission evidence |
| `test-data-permission-coverage.ps1` | `PermissionCoverageTest` over synthetic multi-record scope fixtures |
| `test-incident-drill.ps1` | `IncidentDrillTest` over nine strict synthetic scenarios and dependency/CLI verification |
| `test-feed-completeness-audit.ps1` | `FeedAuditTest` over explicit schedules/policies, verified journals, anomaly/rejection cases, and deterministic artifacts |

Some runners intentionally repeat shared regression checks. Compiling Java
sources does not establish that every test class was executed. This workflow
also runs packaged daily-operations, dataset intended-use, multi-record data-permission, incident-drill, and feed-audit checks after the production JAR is built. It builds and tests the standalone permission-coverage JAR, then checks the same 102-scenario suite against the production JAR. The nine incident-drill scenarios, including the 198-check acceptance suite, dependency inspection, repeated executions, and manifest verification, run against both the standalone and production JARs. The feed audit and synthetic drill also run against the production JAR. It does not invoke the
option-pricer, instrument-sequence, mapping-registry, or synchronized-bar-frame
runners. It does not establish full repository test coverage, power-loss safety,
statistical validity, data rights, or trading performance. The process harness
does not simulate power loss. The Sharpe HAC suite qualifies only its three fixed
synthetic processes and establishes no general coverage claim.

Every runner's process exit code is checked. All selected suites are attempted
even if one fails; any failure makes the CI step fail and skips the production
build. After all suites pass, `Intra-Paper-System/build.ps1` creates
`intra-paper-system.jar`. CI reads `META-INF/MANIFEST.MF` from that actual JAR,
unfolds continuation lines, and requires exactly one `Build-Commit` equal to both
`git rev-parse HEAD` and `GITHUB_SHA`. For pull requests this is the checked-out
GitHub merge revision, not necessarily the contributor's branch tip. Dirty or
unknown build identities fail this check. The daily-operations checker and its
synthetic drill also run against the packaged JAR before the manifest is accepted.

CI requires a clean checkout before testing and checks it again before the
production build. Its output directory must be absent or empty, outside the
source checkout, and have no reparse points in existing ancestors. Reusing output
requires a new directory; this prevents stale logs or a previous JAR from being
mistaken for this run's results. Existing runners' ignored `build/` directories
do not make the source checkout dirty.

## Logs and artifact retention

| Path on runner | Contents / artifact |
| --- | --- |
| `${RUNNER_TEMP}/intra-paper-jdk/install.log` | Pinned JDK version, archive URL, expected/actual SHA-256, installation status |
| `${RUNNER_TEMP}/intra-paper-ci/logs/environment.log` | JDK vendor, Java/runtime/compiler versions, PowerShell version, source and expected commit, planned suites |
| `${RUNNER_TEMP}/intra-paper-ci/logs/<suite>.log` | Runner name, source commit, stdout/stderr, result and exit code |
| `${RUNNER_TEMP}/intra-paper-ci/logs/production-build.log` | Production build output and exit code |
| `${RUNNER_TEMP}/intra-paper-ci/logs/manifest-check.log` | Expected and embedded commit, verified JAR SHA-256 |
| `${RUNNER_TEMP}/intra-paper-ci/logs/summary.log` | Overall status and actual `PASS`, `FAIL`, or `NOT_RUN` result for every suite/check |
| `${RUNNER_TEMP}/intra-paper-ci/logs/failure.log` | CI exception, when a failure occurs |
| `${RUNNER_TEMP}/intra-paper-ci/package/intra-paper-system.jar` | Production JAR, uploaded only after successful validation |

The workflow uploads logs with `always()` as
`offline-validation-logs-<github.sha>-<github.run_attempt>`, including on test or
manifest failure. It uploads the verified JAR separately as
`intra-paper-system-<github.sha>-<github.run_attempt>`. Both artifacts have
**14-day retention**. An upload with no matching files is an error. The log upload
accepts whichever configured paths exist: an installer failure can have only
`install.log`, and a skipped build has no build/manifest log. `if-no-files-found`
does not require every individual log path to exist. A successful JAR upload
requires the single specified production JAR. The Actions step summary
also lists the source commit, JDK version and actual suite/check results.
Generated fixture directories, compiled test classes and intermediate JARs are
not uploaded; the retained text contains the focused runners' concise output.

## Reproduce and verify failure propagation

Use a clean checkout containing the workflow changes and the supported Microsoft
JDK. From the repository root:

```powershell
$env:JAVA_HOME = 'C:\path\to\jdk-21.0.13.0.2+1'
.\.github\scripts\test-offline-ci.ps1 `
    -OutputRoot (Join-Path $env:TEMP 'intra-paper-ci-local') `
    -ExpectedCommit (git rev-parse HEAD)
```

To test the installer locally, pass a fresh `-InstallRoot` below the system
temporary directory explicitly. Pass a fresh output directory outside the
checkout on every validation run. The existing replay/evaluation runners also use ignored
`Intra-Paper-System/build/` output paths.

Use short checkout/output paths on Windows: the existing runners pass source
paths directly to `javac`, so deeply nested copies can exceed Windows command
line or file path limits. GitHub's normal checkout and `RUNNER_TEMP` paths are
short.

For hosted acceptance, after authorization to push a test branch, open a pull
request targeting `main` and retain the successful run URL and artifact names.
On a separate disposable commit, insert
`if (args.length == 0) throw new AssertionError("intentional CI failure");`
at the start of `PortfolioAccountingLedgerTest.main`. Its runner passes no
arguments, so the Java test fails. The workflow must finish nonzero, retain a
`portfolio-accounting.log` with the assertion and nonzero exit, report that
suite as `FAIL`, and report production build/manifest as `NOT_RUN`; no production
JAR artifact should be uploaded. Restore the test in the disposable branch.
Never include the deliberate failure in the proposed production change.

Local execution verifies runner/build/failure behavior but is not evidence of a
hosted Actions run. A hosted test-branch run requires separate push authorization;
neither this workflow nor its scripts push or merge code.

## Reviewed local integration validation

The isolated validation worktree is based on reviewed integration branch
`codex/local-integration-reviewed-20261106`, revision
`07e5483b8bd5afe744fed9712198aabea91b02b3`. Only this guide, the workflow and its
two CI scripts were copied from the original checkout. The original checkout is
left unchanged. The task branch is `codex/windows-java21-ci-reviewed-20261107`.

Local evidence is retained separately under the system temporary directory in
`ci21v-20261107/`: `p/intra-paper-ci/logs/`, `n/intra-paper-ci/logs/`, the successful JAR,
installer/validator output, executable version checks, and `validation-report.md`
with tested revisions and hashes. The failed test is inserted only in a separate
disposable clone of the task worktree and restored afterward. No deliberate
failure or generated output belongs in the task branch's diff.

This is local validation; GitHub provisioning and artifact uploads require an
authorized hosted run. The local checks inspect upload conditions and resolve
artifact paths without invoking GitHub or using credentials. No hosted success,
push or merge is implied.
